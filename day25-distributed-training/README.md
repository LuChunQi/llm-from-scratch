# Day 25: 分布式训练 — 从单卡到千卡集群的扩展之道

## 🔗 上节回顾

昨天我们拆解了 MoE（混合专家模型）——把 FFN 拆成多个专家，每次只激活一部分，实现"参数多、计算少"。Mixtral 8×7B 用 47B 的总参数、12.9B 的激活参数，就达到了接近 34B Dense 模型的效果。但我们也留下了一个关键问题：**8 个专家在一台机器上放不下怎么办？** 答案是 Expert Parallelism——把不同专家放到不同 GPU 上，用 All-to-All 通信协调。这其实就是**分布式训练**的一个缩影。今天，我们把视角从"MoE 的专家并行"拉升到更宏观的层面——当你需要训练一个 70B 甚至 405B 的模型时，怎么把计算拆到成百上千张 GPU 上？

## 🌊 第一个问题：单卡的"天花板"

> ❓ **问题**：我们已经在前面 24 天里写了很多模型。但如果你真的想训练一个"能用"的模型——哪怕只有 7B 参数——单张 GPU 够吗？

### 算一笔账：训练一个 7B 模型需要什么

```
以 LLaMA-2-7B 为例：

模型参数：
  7B = 70 亿参数

训练内存（混合精度，Adam 优化器）：
  模型参数（FP16）：      7B × 2 bytes = 14 GB
  梯度（FP16）：          7B × 2 bytes = 14 GB
  Adam 状态（FP32）：      7B × 4 × 2 = 56 GB  （一阶 + 二阶动量）
  激活值（取决于 batch/seq_len）：~10-30 GB
  
  总计：~94-114 GB 仅仅为了装下训练状态！

单张 GPU 的显存：
  RTX 4090：24 GB → 装不下（连模型参数都放不全）
  A100-40G：40 GB → 勉强装下模型+梯度，但 Adam 状态放不下
  A100-80G：80 GB → 可以用一些技巧（梯度检查点、混合精度）勉强训练
  H100-80G：80 GB → 同上，但计算更快

训练计算量估算（Chinchilla Scaling Laws）：
  一个 token 的训练 FLOPs ≈ 6 × 参数量
  7B 模型训练 1T tokens：
    6 × 7B × 1T = 4.2 × 10^22 FLOPs
  
  H100 算力：~989 TFLOPS (FP16/BF16)
  
  单张 H100 训练时间：
    4.2 × 10^22 / (989 × 10^12 × 3600) ≈ 11,800 小时 ≈ 491 天
    
  → 用 1 张 H100 训练 7B 模型需要近 1.5 年！

如果有 256 张 H100：
  491 天 / 256 ≈ 1.9 天
  
  → 但前提是：这 256 张卡能高效协同工作
  → 这就是分布式训练要解决的问题
```

### 更大的模型呢？

```
LLaMA-3-70B：
  参数：70B
  训练数据：~10T tokens
  训练 FLOPs：6 × 70B × 10T = 4.2 × 10^24
  
  单张 H100：49,100 天 ≈ 134 年
  2048 张 H100：~24 天

LLaMA-3-405B：
  参数：405B
  训练数据：~15T tokens
  训练 FLOPs：6 × 405B × 15T = 3.6 × 10^25
  
  单张 H100：419,000 天 ≈ 1,147 年
  16384 张 H100：~25.6 天

结论：
  训练大模型 = 海量计算 + 海量内存
  单卡根本不可能完成
  → 必须分布式训练
```

## 🧱 第二个问题：分布式训练的三大基本策略

> ❓ **问题**：把训练拆到多张卡上，说起来容易，但具体怎么拆？模型、数据、计算——哪个维度拆？

分布式训练有三种基本策略，它们解决不同的问题，也可以组合使用：

```
三种基本并行策略：

1. 数据并行（Data Parallelism, DP）
   → 每张卡持有一份完整模型副本
   → 数据拆成多份，每张卡处理不同的数据
   → 解决"数据太多，训练太慢"

2. 张量并行（Tensor Parallelism, TP）
   → 把一层内的矩阵拆到多张卡上
   → 每张卡持有模型参数的一部分
   → 解决"模型太大，单卡装不下"

3. 流水线并行（Pipeline Parallelism, PP）
   → 把模型的不同层拆到不同卡上
   → 数据像流水线一样依次流过各卡
   → 解决"模型太深，单卡装不下"
```

## 📦 第三个问题：数据并行（Data Parallelism）— 最直觉的加速方式

> ❓ **问题**：最简单的分布式训练方式是什么？如果模型能放进单卡，但训练太慢，怎么办？

**数据并行**是最容易理解的策略：每张卡拿一份模型副本，但处理不同的数据。

### 核心流程

```
假设 4 张 GPU，batch_size = 32：

Step 1: 数据拆分
  全局 batch (32 条样本)
    → GPU 0: mini-batch (8 条)
    → GPU 1: mini-batch (8 条)
    → GPU 2: mini-batch (8 条)
    → GPU 3: mini-batch (8 条)

Step 2: 前向传播（各自独立）
  每张 GPU 用自己的 mini-batch 独立做前向传播
  → 每张 GPU 得到各自的 loss

Step 3: 梯度同步（All-Reduce）
  每张 GPU 反向传播计算各自的梯度
  → 所有 GPU 通过 All-Reduce 通信，取梯度平均
  → 每张 GPU 得到相同的平均梯度

Step 4: 参数更新（各自独立）
  每张 GPU 用相同的平均梯度更新各自的模型副本
  → 所有 GPU 的参数保持一致

类比：
  4 个学生，每人有一本相同的教材（模型副本）
  老师把 32 道作业题分给 4 个学生（数据拆分）
  每人做 8 道题，算出自己的错题分析（梯度）
  然后大家开会，汇总错题分析（All-Reduce）
  最后每个人都根据汇总结果订正教材（参数更新）
```

### All-Reduce：数据并行的核心通信原语

```
All-Reduce 的含义：
  所有 GPU 各持有一个张量 → 汇总计算（求和/平均）→ 结果分发给所有 GPU

  GPU 0: grad = [1, 2, 3]
  GPU 1: grad = [4, 5, 6]
  GPU 2: grad = [7, 8, 9]
  GPU 3: grad = [10, 11, 12]
  
  All-Reduce (avg) 后：
  GPU 0: [5.5, 6.5, 7.5]
  GPU 1: [5.5, 6.5, 7.5]
  GPU 2: [5.5, 6.5, 7.5]
  GPU 3: [5.5, 6.5, 7.5]

Ring All-Reduce（环形规约，最高效的实现）：

  假设 4 张 GPU 排成一个环：

  Step 1: Reduce-Scatter（每张 GPU 负责一部分数据的汇总）
    GPU 0 → GPU 1: 发送 grad[0]
    GPU 1 → GPU 2: 发送 grad[1]
    GPU 2 → GPU 3: 发送 grad[2]
    GPU 3 → GPU 0: 发送 grad[3]
    （经过 log(N) 轮后，每张 GPU 拥有完整求和的一部分）

  Step 2: All-Gather（把汇总结果分发给所有人）
    反向传递，每张 GPU 把自己汇总的部分发出去
    （经过 log(N) 轮后，每张 GPU 拥有完整的平均梯度）

  通信量：
    每张 GPU 发送/接收：2 × (N-1)/N × 梯度大小
    → 几乎等于 2 倍梯度大小，与 GPU 数量 N 无关！
    → 这就是 Ring All-Reduce 的魅力：GPU 越多，效率越高

  对比朴素的 Parameter Server：
    PS 方案：一台中心服务器收集所有梯度，平均后分发
    → 中心服务器是瓶颈：带宽 = N × 梯度大小
    → N 越大，PS 越慢
    
    Ring：没有中心瓶颈，通信量恒定
```

### DDP（Distributed Data Parallel）— PyTorch 的标准实现

```
PyTorch DDP 的关键设计：

1. Process Group（进程组）
   每个 GPU 对应一个独立进程
   进程间通过 NCCL（NVIDIA Collective Communication Library）通信

2. Gradient Bucket（梯度桶）
   不是等所有梯度算完再通信，而是：
   → 把梯度分成多个"桶"（bucket）
   → 一个桶的梯度算完，立即开始通信
   → 通信和计算重叠（Overlap）！

   时间线：
   ┌─────────────────────────────────────────┐
   │ 计算：  [层6梯度] [层5梯度] [层4梯度] ...│
   │ 通信：         [层6桶] [层5桶] [层4桶] ...│
   └─────────────────────────────────────────┘
   → 计算和通信并行，大大减少等待时间

3. 模型一致性保证
   DDP 保证每张卡的模型参数在每步结束后完全一致
   → 使用 All-Reduce 同步梯度，然后用相同的 optimizer 更新

DDP 的限制：
  每张 GPU 必须能装下完整模型 + 优化器状态
  → 7B 模型 + Adam：~94GB → A100-80G 都不够
  → 纯 DDP 训练 7B 模型在 A100-80G 上需要梯度检查点等技巧
  → 更大的模型（70B+）？完全不可能
```

### ZeRO：数据并行的进化

> ❓ **问题**：DDP 的致命问题是每张卡都存一份完整的模型+优化器。70B 模型一张卡都装不下，怎么 DDP？

**ZeRO（Zero Redundancy Optimizer）** 来自微软 DeepSpeed 团队，核心思想：**数据并行中，每张卡存了完整的模型+优化器状态，这是巨大的冗余！把这些冗余状态也拆分到不同卡上。**

```
DDP 的内存冗余：

4 张 GPU 训练 7B 模型：
  GPU 0: 模型(14GB) + 梯度(14GB) + Adam(56GB) = 84GB
  GPU 1: 模型(14GB) + 梯度(14GB) + Adam(56GB) = 84GB
  GPU 2: 模型(14GB) + 梯度(14GB) + Adam(56GB) = 84GB
  GPU 3: 模型(14GB) + 梯度(14GB) + Adam(56GB) = 84GB
  总计：336GB！
  
  但真正需要的只有：1份模型 + 1份梯度 + 1份Adam = 84GB
  冗余：336GB - 84GB = 252GB（75% 是浪费！）

ZeRO 的三级优化：

┌──────────────────────────────────────────────────────────────────────┐
│  级别      │  拆分什么          │  每卡内存              │  通信量   │
├──────────────────────────────────────────────────────────────────────┤
│  ZeRO-1    │  优化器状态        │  84GB / 4 = 35GB       │  = DDP   │
│  ZeRO-2    │  优化器 + 梯度     │  (84-56-14)/4 + ...    │  = DDP   │
│  ZeRO-3    │  优化器+梯度+参数  │  84GB / 4 = 21GB      │  1.5×DDP │
└──────────────────────────────────────────────────────────────────────┘

ZeRO-3 详解（最激进的拆分）：
  GPU 0: 持有参数的 1/4（如第 0-25% 的参数切片）
  GPU 1: 持有参数的 1/4（如第 25-50% 的参数切片）
  GPU 2: 持有参数的 1/4（如第 50-75% 的参数切片）
  GPU 3: 持有参数的 1/4（如第 75-100% 的参数切片）

  前向传播时：
  → 需要 W1 做计算？向持有 W1 的 GPU 请求（All-Gather）
  → 用完立即释放（不常驻内存）
  
  反向传播时：
  → 需要某层的梯度？向持有该参数的 GPU Reduce-Scatter
  → 每张 GPU 只保留自己那部分梯度

ZeRO-3 的代价：
  通信量 = DDP 的 1.5 倍（多了一次 All-Gather 获取参数）
  → 但换来了 4 倍的内存节省！
  → 64 张 GPU 用 ZeRO-3：理论上可以训练 64 × 单卡内存 的模型

类比：
  DDP：4 个学生，每人有一套完整教材（14GB），太浪费
  ZeRO-1：教材共享，但笔记本（优化器状态）各拿 1/4
  ZeRO-2：教材 + 作业（梯度）都各拿 1/4
  ZeRO-3：所有东西都各拿 1/4，需要时互相借阅
```

## ✂️ 第四个问题：张量并行（Tensor Parallelism）— 把矩阵切开

> ❓ **问题**：ZeRO 解决了数据并行的内存冗余，但它仍然是"逻辑上的数据并行"——每张卡在某一时刻需要完整参数。如果一层都装不下呢？

**张量并行（TP）** 的思路更暴力：**直接把一层内的矩阵按列/行切到不同 GPU 上。**

### 线性层的切分

```
标准线性层：Y = X @ W

  X: (batch, d_model)     如 (4, 4096)
  W: (d_model, d_out)     如 (4096, 14336)
  Y: (batch, d_out)       如 (4, 14336)

张量并行：把 W 按列切成 2 份

  GPU 0: W_0 = W[:, :7168]    前 7168 列
  GPU 1: W_1 = W[:, 7168:]    后 7168 列

  GPU 0: Y_0 = X @ W_0    → (4, 7168)
  GPU 1: Y_1 = X @ W_1    → (4, 7168)

  然后拼接：Y = [Y_0, Y_1]  → (4, 14336)

  → 每张 GPU 只存 W 的一半，计算也只做一半

但等等——X 需要在两张 GPU 上都有！
  → X 需要广播（Broadcast）给所有 GPU
  → 或者 X 在上一步已经通过通信获得了
```

### Transformer 层的张量并行（Megatron-LM 方案）

```
Transformer 层的两个主要组件：
  1. Multi-Head Attention
  2. Feed-Forward Network (FFN)

关键洞察：
  MHA 的多个 Head 天然可以并行！
  FFN 的中间层也可以按列切分！

具体切法（以 2 张 GPU 为例）：

=== Multi-Head Attention ===

标准：QKV 投影 + 多头注意力 + 输出投影

张量并行：
  8 个 Head → GPU 0 负责 Head 0-3, GPU 1 负责 Head 4-7
  
  GPU 0:
    W_Q0, W_K0, W_V0 (只包含 Head 0-3 的参数)
    → 独立计算 Head 0-3 的注意力 → attn_output_0
  
  GPU 1:
    W_Q1, W_K1, W_V1 (只包含 Head 4-7 的参数)
    → 独立计算 Head 4-7 的注意力 → attn_output_1

  输出投影也切开：
    GPU 0: W_O0 = W_O[:, :2048]
    GPU 1: W_O1 = W_O[:, 2048:]
  
  GPU 0: output_0 = attn_output_0 @ W_O0
  GPU 1: output_1 = attn_output_1 @ W_O1

  All-Reduce: output = output_0 + output_1  ← 关键！
  → 两张 GPU 的输出求和，得到完整输出

=== Feed-Forward Network ===

FFN: Y = GeLU(X @ W1) @ W2

第一层 W1 按列切：
  GPU 0: W1_0 = W1[:, :7168]
  GPU 1: W1_1 = W1[:, 7168:]

  GPU 0: Y1_0 = GeLU(X @ W1_0)   → (batch, 7168)
  GPU 1: Y1_1 = GeLU(X @ W1_1)   → (batch, 7168)

第二层 W2 按行切（配合 W1 的列切）：
  GPU 0: W2_0 = W2[:7168, :]    → (7168, 4096)
  GPU 1: W2_1 = W2[7168:, :]    → (7168, 4096)

  GPU 0: Y_0 = Y1_0 @ W2_0     → (batch, 4096)
  GPU 1: Y_1 = Y1_1 @ W2_1     → (batch, 4096)

  All-Reduce: Y = Y_0 + Y_1     ← 又是求和！

关键观察：
  一个 Transformer 层只需要 2 次 All-Reduce（MHA 后 + FFN 后）
  → 通信量不大（只传输激活值，不传输参数）
  → 计算和通信的比例很好

  但 TP 只适合"节点内"（同一台机器的 GPU）
  → 节点内用 NVLink 连接，带宽 ~900 GB/s
  → 节点间用 InfiniBand，带宽 ~100 GB/s
  → TP 通信量大，跨节点太慢
```

### TP 的通信模式

```
TP 的通信特点：

  每个 Transformer 层：2 次 All-Reduce
  32 层模型：64 次 All-Reduce
  
  每次 All-Reduce 的数据量：
    激活值大小 = batch_size × seq_len × d_model
    如 2 × 2048 × 4096 × 2 bytes = 32 MB（BF16）
  
  NVLink 延迟：~10 μs + 32MB / 900GB/s ≈ 36 μs
  → 每次通信 ~46 μs，64 次 ≈ 3 ms
  
  对比一次前向传播的计算时间：~50 ms
  → 通信占比 ~6% → 可以接受！

跨节点（InfiniBand）：
  32MB / 100GB/s ≈ 320 μs
  → 64 次 ≈ 20 ms
  → 通信占比 ~40% → 不可接受！

结论：TP 通常只在同一节点内使用（如 8 卡一台的机器）
  TP 度 = 节点内 GPU 数 = 8（典型配置）
```

## 🏭 第五个问题：流水线并行（Pipeline Parallelism）— 模型的"工厂流水线"

> ❓ **问题**：张量并行把一层内的参数拆开了，但需要高速通信（NVLink）。如果模型太深（100+ 层），即使每层都用 TP 也装不下呢？或者需要跨节点通信呢？

**流水线并行（PP）** 的思路是按**层**拆模型——不同 GPU 负责不同的层，数据像流水线一样依次通过。

### 最朴素的思路：串行

```
32 层模型，4 张 GPU：

  GPU 0: 层 0-7    (Layer 0 ~ Layer 7)
  GPU 1: 层 8-15
  GPU 2: 层 16-23
  GPU 3: 层 24-31 + 输出头

前向传播（串行）：
  数据 → GPU 0 → GPU 1 → GPU 2 → GPU 3 → 输出

反向传播（串行，反向）：
  梯度 → GPU 3 → GPU 2 → GPU 1 → GPU 0

问题（气泡 Bubble）：
  ┌────────────────────────────────────────────────────┐
  │ GPU 0: [前向]         [等待...]         [反向]     │
  │ GPU 1:    [等待] [前向]     [等待...] [反向]       │
  │ GPU 2:       [等待...] [前向]     [反向]          │
  │ GPU 3:          [等待...] [前向] [反向]            │
  └────────────────────────────────────────────────────┐
  
  → GPU 利用率极低！大部分时间在等待
  → 这就是"气泡"——流水线中的空闲时间
```

### 微批次流水线（Micro-batch Pipeline）

> ❓ **问题**：气泡太多了，能不能让不同 GPU 同时工作？

**核心思想**：把一个大 batch 拆成多个 micro-batch，让它们像流水线上的产品一样，一个接一个地通过。

```
GPipe 方案（Google, 2019）：

假设 batch 拆成 4 个 micro-batch（m0, m1, m2, m3）

时间步：  t1      t2      t3      t4      t5      t6      t7      t8
  GPU 0: [m0前向] [m1前向] [m2前向] [m3前向]         [m3反向] [m2反向] [m1反向] [m0反向]
  GPU 1:         [m0前向] [m1前向] [m2前向] [m3前向]         [m3反向] [m2反向] [m1反向] [m0反向]
  GPU 2:                  [m0前向] [m1前向] [m2前向] [m3前向]         [m3反向] [m2反向] [m1反向]
  GPU 3:                           [m0前向] [m1前向] [m2前向] [m3前向] [m3反向] [m2反向] [m1反向]

气泡仍然存在（开始和结束的预热/排空阶段），但大幅减少！

气泡比例 ≈ (P - 1) / (M + P - 1)
  P = 流水线阶段数（GPU 数）
  M = micro-batch 数

  P=4, M=4: 气泡 = 3/7 ≈ 43%
  P=4, M=16: 气泡 = 3/19 ≈ 16%
  P=4, M=64: 气泡 = 3/67 ≈ 4.5%

  → micro-batch 越多，气泡越少，GPU 利用率越高

  类比：
    工厂流水线生产 4 辆车 vs 64 辆车
    → 4 辆车时，流水线频繁启停，效率低
    → 64 辆车时，流水线满负荷运转，效率高

1F1B 调度（One Forward One Backward）：
  改进 GPipe 的调度，交替做前向和反向：

  GPU 0: [m0前] [m1前] [m2前] [m0反] [m3前] [m1反] [m2反] [m3反]
  GPU 1:        [m0前] [m1前] [m0反] [m2前] [m1反] [m3前] [m2反] [m3反]
  ...

  → 更早释放中间激活值的内存
  → 内存效率更高（不需要存所有 micro-batch 的激活值）
```

### PP 的通信

```
PP 的通信特点：

  每个 micro-batch 在相邻 GPU 间传递激活值和梯度
  → 点对点通信（Send/Recv），不是 All-Reduce
  
  通信量：
    激活值大小 = batch_size × seq_len × d_model × 2 bytes
    但每个 micro-batch 只在相邻 GPU 间传递一次
    
  → 通信量远小于 TP（TP 每层都要 All-Reduce）
  → PP 适合跨节点部署！

  但 PP 的代价是气泡 → GPU 利用率不如 TP
```

## 🧩 第六个问题：三维混合并行 — 训练大模型的"黄金配方"

> ❓ **问题**：数据并行、张量并行、流水线并行各有优缺点。训练一个 70B 模型（需要 1000+ 张 GPU），只用一种并行策略肯定不够。怎么组合它们？

### 三维混合并行的配置

```
以训练 LLaMA-2-70B 为例（2048 张 A100-80G）：

维度分解：
  TP（张量并行）= 8   （同一节点内的 8 张 GPU，NVLink 连接）
  PP（流水线并行）= 4  （4 个流水线阶段，跨节点）
  DP（数据并行）= 64   （64 路数据并行）

  总 GPU 数 = TP × PP × DP = 8 × 4 × 64 = 2048

  每个 DP 组的拓扑：
    节点 0（8 张 GPU）: TP=8，持有模型的前 1/4 层
    节点 1（8 张 GPU）: TP=8，持有模型的第 2 个 1/4 层
    节点 2（8 张 GPU）: TP=8，持有模型的第 3 个 1/4 层
    节点 3（8 张 GPU）: TP=8，持有模型的最后 1/4 层

    这 4 个节点组成一个 PP 组（流水线）
    
    64 个这样的 PP 组形成 DP 组
    → 64 条流水线同时处理不同的数据

  每个 DP 组的 GPU 数 = TP × PP = 32
  DP 组数 = 2048 / 32 = 64

  每张 GPU 的内存（粗略）：
    模型参数：70B × 2 / (TP × PP) = 140GB / 32 ≈ 4.4GB
    优化器状态：70B × 12 / 32 ≈ 26.3GB  （Adam FP32 + 一阶 + 二阶）
    梯度：70B × 2 / 32 ≈ 4.4GB
    激活值：~10GB
    总计：~45GB → A100-80G 放得下！
```

### 通信模式总结

```
三种并行的通信模式对比：

┌──────────────────────────────────────────────────────────────────────┐
│  并行方式  │  通信类型     │  通信频率    │  适合网络    │  通信量    │
├──────────────────────────────────────────────────────────────────────┤
│  TP       │  All-Reduce  │  每层 2 次   │  NVLink     │  大        │
│  PP       │  Send/Recv   │  每层 1 次   │  InfiniBand │  中        │
│  DP       │  All-Reduce  │  每步 1 次   │  InfiniBand │  大        │
└──────────────────────────────────────────────────────────────────────┘

配置原则：
  1. TP = 节点内 GPU 数（通常 4 或 8）→ 利用 NVLink 高带宽
  2. PP = 模型层数 / 每个 TP 组能装的层数 → 按需确定
  3. DP = 总 GPU / (TP × PP) → 用剩余 GPU 做数据并行加速
```

## 🔬 第七个问题：混合精度训练 — 不只是"把 FP32 换成 FP16"

> ❓ **问题**：分布式训练解决了"怎么拆"的问题，但训练效率还有一个关键优化——混合精度。它不只是"用低精度浮点数"这么简单，里面有很多精巧的设计。

### BF16 vs FP16 vs FP32

```
精度对比：

┌──────────────────────────────────────────────────────────┐
│  格式   │  指数位  │  尾数位  │  范围         │  精度     │
├──────────────────────────────────────────────────────────┤
│  FP32  │  8 bit   │  23 bit  │  ±3.4×10^38  │  7 位十进制│
│  FP16  │  5 bit   │  10 bit  │  ±6.5×10^4   │  3 位十进制│
│  BF16  │  8 bit   │  7 bit   │  ±3.4×10^38  │  2 位十进制│
└──────────────────────────────────────────────────────────┘

关键区别：
  FP16：范围小（容易溢出），精度高
  BF16：范围大（不容易溢出），精度低
  
  训练时最怕的是梯度溢出（NaN）
  → BF16 的范围和 FP32 一样，几乎不会溢出
  → 所以现代训练都用 BF16

  为什么不全用 BF16？
  → BF16 精度低（只有 7 位尾数）
  → 参数更新时微小的变化可能被舍入掉
  → 所以 optimizer 用 FP32（"主权重"保持 FP32）
```

### 混合精度的完整流程

```
AMP (Automatic Mixed Precision) 的训练流程：

  存储：模型参数有 FP32 主副本（master weight）
  前向：用 BF16/FP16 做前向传播（速度快、内存省）
  损失：FP32 计算损失（避免精度损失）
  反向：BF16/FP16 做反向传播（速度快）
  更新：梯度转 FP32 → 用 FP32 主权重更新 → 再转回 BF16

  Step-by-step：
  1. 取出 FP32 主权重 W_fp32
  2. 转成 BF16: W_bf16 = W_fp32.to(bf16)
  3. 前向传播用 W_bf16 → output_bf16
  4. 计算 loss_fp32（用 FP32）
  5. 反向传播得到梯度 grad_bf16
  6. 梯度转 FP32: grad_fp32 = grad_bf16.to(fp32)
  7. 更新: W_fp32 = W_fp32 - lr × grad_fp32
  8. 下一步重复
  
  内存节省：
    前向/反向都用 BF16（2 bytes vs 4 bytes）
    → 激活值内存减半！
    → 这是大 batch 训练的关键
  
  速度提升：
    BF16 的矩阵乘法在 Tensor Core 上速度是 FP32 的 2-8 倍
    → A100: FP32 matmul ~19.5 TFLOPS, BF16 matmul ~312 TFLOPS
    → 16 倍的算力差距！
```

## 🔑 关键洞察

1. **分布式训练的本质是"分而治之"**：数据并行分数据，张量并行分矩阵，流水线并行分层——三种策略各有所长，组合使用才能训练超大模型
2. **数据并行最简单但最耗内存**：每张卡存完整模型副本。ZeRO 通过拆分优化器状态/梯度/参数来消除冗余
3. **张量并行通信最频繁**：每层需要 2 次 All-Reduce，只能在 NVLink（节点内）使用
4. **流水线并行有"气泡"**：GPU 会空闲等待，但通信量小，适合跨节点
5. **三维混合并行是工业标准**：TP 节点内 + PP 跨节点 + DP 加速 = 训练 70B+ 模型的标配
6. **混合精度不只是"换个数据类型"**：FP32 主权重 + BF16 前向反向 + Loss Scaling = 速度翻倍、内存减半

## 📝 一句话总结

> 分布式训练是训练大模型的必经之路。数据并行（DP）通过复制模型、拆分数据来加速——但每张卡都存完整副本太浪费，ZeRO 把优化器状态/梯度/参数也拆开，用通信换内存。张量并行（TP）把一层内的矩阵按列/行切到不同 GPU——通信频繁，只在 NVLink 节点内使用。流水线并行（PP）按层拆模型，数据像工厂流水线一样流过各 GPU——通信少但有气泡。真实训练中，三种并行组合使用（TP×PP×DP），加上混合精度（BF16 前向 + FP32 更新），才能高效训练 70B、405B 级别的模型。

## 📖 关键术语速查

| 术语 | 含义 |
|------|------|
| **DP** | Data Parallelism，数据并行，每卡存完整模型，拆分数据 |
| **TP** | Tensor Parallelism，张量并行，按列/行切分矩阵到不同 GPU |
| **PP** | Pipeline Parallelism，流水线并行，按层拆分模型到不同 GPU |
| **All-Reduce** | 集合通信原语，所有 GPU 各出数据，汇总后分发给所有人 |
| **Ring All-Reduce** | 环形规约，最高效的 All-Reduce 实现，通信量与 GPU 数无关 |
| **ZeRO** | Zero Redundancy Optimizer，消除数据并行的内存冗余 |
| **气泡（Bubble）** | 流水线并行中 GPU 空闲等待的时间 |
| **微批次（Micro-batch）** | 把一个 batch 拆成多个小批次，填满流水线 |
| **GPipe** | Google 提出的流水线并行方案，先做所有前向再做所有反向 |
| **1F1B** | One Forward One Backward，交替前向反向，更省内存 |
| **AMP** | Automatic Mixed Precision，自动混合精度训练 |
| **BF16** | Bfloat16，指数位和 FP32 相同，不容易溢出 |
| **NVLink** | GPU 之间的高速互联，带宽 ~900 GB/s |
| **InfiniBand** | 节点间高速网络，带宽 ~100-400 GB/s |
| **NCCL** | NVIDIA Collective Communication Library，GPU 集合通信库 |
| **Megatron-LM** | NVIDIA 的大模型分布式训练框架，提出张量并行方案 |
| **DeepSpeed** | 微软的分布式训练框架，提出 ZeRO 优化 |
