# Day 23: 量化进阶 — AWQ、GGUF、BitsAndBytes，聪明量化的艺术

## 🔗 上节回顾

昨天我们手写了线性量化器，亲眼看到了 INT8 几乎无损、INT4 微小误差、INT2 通常不可用的实验结果。我们学到了量化的核心公式——scale 和 zero_point 组成的线性映射，也知道了逐通道量化比逐张量量化精度更高。但我们留下了一个关键问题：**线性量化对所有权重"一视同仁"，用同一个 scale 把它们压进整数格子里。可如果某些权重特别重要呢？一刀切的量化会不会伤到模型的"命门"？** 今天，我们就来看看业界是怎么"聪明地"量化的。

---

## 🌊 第一个问题：为什么"一刀切"的线性量化不够好？

> ❓ **问题**：上节课我们的线性量化器已经能把 7B 模型压到 3.5GB 了，精度损失也才 1-3%。为什么还需要更复杂的量化方法？

答案藏在三个现实问题里：

### 问题 1：离群值（Outliers）

```
想象一个 4096 维的权重向量，99% 的值在 [-0.3, 0.3] 之间，
但有 10 个值超过了 5.0。

线性量化：scale = (5.0 - (-5.0)) / 15 ≈ 0.67（INT4）
  → 那 99% 的"正常"权重只能用 [-0.45, 0.45] 范围内的几个级别
  → 精度被那 10 个"捣蛋鬼"拖垮了！

类比：
  一个班 30 个学生，28 个考了 60-80 分，2 个考了 100 分
  老师如果按"全班平均 75 分"来教，那 2 个尖子生觉得太简单
  但如果按"全班最高 100 分"来教，28 个普通学生会跟不上
  
  关键问题：少数极端值决定了量化的 scale
  → 大多数权重被迫用很粗的粒度来表示
```

### 问题 2：不同层的敏感度差异巨大

```
上节课末尾提过：不是所有层对量化的承受力一样。

Embedding 层：
  权重分布比较"散"，但每个词的向量表示对下游影响极大
  → INT4 量化后，"开心"和"快乐"可能变得几乎一样 → 语义丢失

Attention 的 Q/K 投影：
  决定了"谁关注谁"的注意力分布
  → 微小的权重变化 → 注意力模式大变 → 模型行为失控

FFN 的中间层：
  参数最多（占模型 2/3），但冗余也最大
  → INT4 甚至 INT3 都扛得住

问题：线性量化不知道哪些层重要
  → 重要层和冗余层用同样的策略 → 整体效果被短板拖累
```

### 问题 3：不同硬件的需求不同

```
GPU（如 RTX 4090）：
  → 支持 INT8/INT4 的 tensor core
  → 需要权重格式方便 GPU 解压

CPU（如 Intel/AMD）：
  → 没有专门的低精度计算单元
  → 需要量化格式方便 CPU 逐个解压

手机/嵌入式：
  → 内存极小（4-8GB）
  → 需要极致压缩，同时保持可用精度

问题：一种量化格式无法满足所有硬件
  → 需要不同的"打包方式"来适配不同设备
```

**这三个问题共同催生了更聪明的量化方案。** 接下来我们按"解决问题的思路"来逐个介绍。

## 🎯 GPTQ：基于二阶信息的逐层量化

> ❓ **问题**：既然逐通道量化能照顾不同通道的差异，能不能更进一步——考虑权重之间的相互影响？

GPTQ（**G**enera**P**ost-**T**raining **Q**uantization）是目前最流行的 4-bit 量化方法之一。它的核心思想：**逐层量化权重时，利用 Hessian 矩阵（二阶导数信息）来补偿量化误差**。

### 从 OBQ 到 GPTQ 的演进

```
故事的起点：OBQ（Optimal Brain Quantization）

假设我们要量化权重矩阵 W 的某一行 w = [w1, w2, ..., wn]：

朴素方法：逐个量化，完了就完了
  w1 → round(w1/scale)  → 误差 e1 = w1 - w1_hat
  w2 → round(w2/scale)  → 误差 e2 = w2 - w2_hat
  ...
  总误差 = e1 + e2 + ... + en

OBQ 的改进：量化一个权重后，调整剩余权重来补偿误差！
  
  第 1 步：量化 w1 → 误差 e1
  第 2 步：不是直接量化 w2，而是先调整 w2...wn 来"抵消" e1
  第 3 步：再量化 w2 → 误差 e2
  第 4 步：调整 w3...wn 来抵消 e2
  ...

  怎么调整？用 Hessian 矩阵 H（损失函数的二阶导数）：
    δw_remaining = -e1 × H_remaining^(-1) × h_1_remaining

  直觉理解：
    你在搭积木塔，每放一块新积木，塔会歪一点
    OBQ = 每放一块，就微调剩余积木的位置来保持塔的平衡
    而 Hessian 矩阵告诉你"往哪边调、调多少"
```

### GPTQ 的关键优化

```
OBQ 的问题：计算量太大
  → 对每个权重都要求 Hessian 的逆 → O(n^4) 复杂度
  → 一个 4096×4096 的矩阵要跑几个小时

GPTQ 的三个关键优化：

优化 1：固定顺序（不再搜索最优顺序）
  OBQ 每次选"Hessian 敏感度最低"的权重先量化
  GPTQ 发现：按任意固定顺序量化，效果几乎一样
  → 省掉了搜索最优顺序的开销

优化 2：批量处理（每次量化一整列）
  不再一个一个量化，而是每次量化一列（B = 128 个权重）
  → 大幅减少 Hessian 逆的更新次数

优化 3：Cholesky 分解缓存
  用 Cholesky 分解预先计算 Hessian 逆的信息
  → 避免数值不稳定

效果：
  OBQ：一个 4096×4096 矩阵量化需要几小时
  GPTQ：整个 175B 模型量化只需 4 小时（GPU）
  
  精度：INT4 量化后， perplexity 只增加 0.1-0.3
```

### GPTQ 的工作流程

```
输入：FP16 模型 + 校准数据集（128 条文本）

For 每一层 Layer_l：
  1. 用校准数据前向传播到这一层，收集输入激活 X
  
  2. 计算 Hessian 矩阵 H = 2 × X^T × X（不需要标签！）
     → 衡量每个权重对输出的"影响力"
  
  3. 将权重矩阵按列分组（每组 B=128 列）
  
  4. For 每组：
     a. 量化这一组的 B 个权重（INT4 对称量化）
     b. 计算量化误差 E
     c. 用 Hessian 逆来调整未量化的权重，补偿误差 E
        → 公式：δW = -E × (H^(-1)[:,quantized] / H^(-1)[quantized,quantized])
  
  5. 输出：量化后的权重 + scale/zero_point（逐组存储）

类比：
  GPTQ 就像一个精密的裁缝在改衣服：
  → 裁掉一寸布（量化一个权重）
  → 立刻检查整件衣服的版型（Hessian 信息）
  → 微调附近的缝线（调整剩余权重）
  → 确保衣服不会因为一处改动而走样
```

## 🛡️ AWQ：保护"重要权重"的量化

> ❓ **问题**：GPTQ 用 Hessian 矩阵做误差补偿，但计算 Hessian 本身就很贵。有没有更简单的方式来保护重要权重？

AWQ（**A**ctivation-aware **W**eight **Q**uantization）提供了一个更优雅的思路：**不补偿误差，而是找到重要权重，给它们乘以一个缩放因子，让它们在量化时受伤害更小**。

### 关键发现：重要权重 ≠ 大权重

```
直觉上的误区：
  "权重的绝对值越大就越重要" → 错！
  
  有些大权重可能只是偏置项，对输出影响不大
  有些小权重可能是关键的注意力权重，改变一点就会影响整个注意力分布

AWQ 的核心洞察：
  一个权重重不重要，取决于它对应的激活值（activation）

  具体来说：权重 w_i 的"重要性" = |w_i| × |activation_i|

  为什么？因为：
  output = Σ (w_i × activation_i)
  
  如果 w_i 很大但 activation_i 总是很小 → 乘积不大 → 对输出影响小
  如果 w_i 很小但 activation_i 总是很大 → 乘积可能很大 → 对输出影响大
  
  → 两者都大的权重才是"关键权重"

类比：
  评估一个员工的重要性，不能只看工资（权重）或工作时长（激活值）
  要看"工资 × 工作效率" = 实际贡献
  一个高薪低效的员工，不如一个中等薪水但超高效率的员工
```

### AWQ 的三步走策略

```
第一步：找重要权重
  用校准数据跑一遍推理
  → 收集每层的激活值
  → 找出 |w_i| × |activation_i| 最大的那些权重
  → 这些就是"salient weights"（显著权重）

第二步：分组 + 找最优缩放因子
  把权重按通道分组
  对每个通道，寻找一个缩放因子 s，使得：
    量化误差(s × w) / s 最小
  
  直觉：
    给重要通道乘以 s > 1 → 放大了数值 → 量化后的相对误差更小
    但 s 不能太大 → 非重要通道的值被压缩 → 误差反而增大
    
    AWQ 用网格搜索在 s ∈ [0.5, 1.0, 1.5, ..., 2.0] 中找最优值

第三步：缩放 + 量化
  W_scaled = W × diag(s)  → 缩放重要通道
  W_quantized = Quantize(W_scaled)  → 正常量化（仍然是 INT4）
  保存 s 作为量化参数的一部分
  
  推理时：
  W_dequantized = Dequantize(W_quantized) × diag(1/s)  → 缩放回来
```

### AWQ 为什么这么有效？

```
数学解释（简化版）：

假设 INT4 量化误差为 ε（≈ scale/2）

对权重 w，量化后的误差 = |w - w_hat| = ε

如果我们把 w 放大 s 倍再量化：
  s × w → 量化 → s × w_hat → 缩放回来 → w_hat / s × s... 不对

实际操作：
  w' = s × w  （先放大）
  w'_hat = Quantize(w')  （量化放大后的值）
  最终误差 = |s × w - w'_hat| / s = ε / s

  所以：s > 1 时，等效误差变小了！
  
但有个陷阱：
  放大 w → 改变了整行的范围 → scale 变大 → ε 也变大
  所以不是"越大越好"，要找到平衡点
  
  AWQ 的网格搜索就是在找这个平衡点
  而且只对重要通道放大，非重要通道保持原样

效果对比（LLaMA-2-7B, INT4）：
  线性量化：perplexity 增加 1.5
  GPTQ：perplexity 增加 0.3
  AWQ：perplexity 增加 0.2
  → AWQ 效果最好，而且不需要计算 Hessian！
```

## 📦 GGUF：CPU 友好的量化格式

> ❓ **问题**：GPTQ 和 AWQ 都是为 GPU 设计的量化方案。那没有 GPU 的设备怎么办？笔记本、树莓派、手机能跑 LLM 吗？

这就是 **GGUF**（**G**eorge **G**eorgiev **U**niversal **F**ormat）出场的时刻——它专门为 CPU 推理优化的量化格式。

### 从 GGML 到 GGUF 的进化

```
GGML 时代：
  llama.cpp 的作者 Georgi Gerganov 开发了 GGML 格式
  → 第一个让 LLM 在 CPU 上跑起来的方案
  → 但 GGML 格式有问题：每次改结构就要 break 兼容性

GGUF 时代（2023 年 8 月）：
  GGUF = GGML 的升级版
  → 使用 key-value 元数据（类似 JSON）存储模型信息
  → 向后兼容，添加新字段不需要 break 旧模型
  → 支持更多量化类型

类比：
  GGML = 自定义二进制格式（脆弱，一改就坏）
  GGUF = 像一个灵活的容器（MP4 之于视频，GGUF 之于模型）
```

### GGUF 的量化类型全家福

```
GGUF 支持的量化类型超过 20 种！以下是主要分类：

┌─────────────────────────────────────────────────────────────┐
│  类型        │  精度   │  每参数字节  │  适用场景           │
├─────────────────────────────────────────────────────────────┤
│  Q8_0        │  8-bit  │   1 byte     │  最高精度，体积大    │
│  Q6_K        │  6-bit  │  0.75 byte   │  高精度，推荐       │
│  Q5_K_M      │  5-bit  │  0.69 byte   │  精度/体积最佳平衡  │
│  Q5_0        │  5-bit  │  0.63 byte   │  Q5_K_M 的简化版    │
│  Q4_K_M      │  4-bit  │  0.58 byte   │  最受欢迎 ⭐        │
│  Q4_0        │  4-bit  │  0.50 byte   │  基础 4-bit         │
│  Q3_K_M      │  3-bit  │  0.43 byte   │  小内存可用         │
│  Q2_K        │  2-bit  │  0.33 byte   │  极限压缩           │
│  Q2_K_S      │  2-bit  │  0.31 byte   │  最小体积           │
└─────────────────────────────────────────────────────────────┘

命名规则：
  Q = Quantized（已量化）
  数字 = 位数（如 Q4 = 4-bit）
  K = k-quant（混合精度量化）
  _M = Medium（中等），_S = Small（小），_L = Large（大）
  _0 = 基础版本（没有混合精度）

关键洞察：K-quant 的"混合精度"
  Q4_K_M 不是所有权重都是 4-bit！
  → 注意力层的关键权重用 6-bit
  → FFN 层用 4-bit
  → 超级不重要的权重用 3-bit
  → 平均下来约 4.5-bit，但精度比纯 4-bit 好得多

类比：
  K-quant 就像一个聪明的旅行打包策略：
  → 贵重物品（重要权重）用硬壳保护（高精度）
  → 衣物（普通权重）用压缩袋（标准精度）
  → 小零碎（不重要权重）随便塞（低精度）
  → 行李箱的总体积最小，但贵重物品安全无损
```

### GGUF 的文件结构

```
一个 GGUF 文件的结构：

┌──────────────────────────────┐
│  GGUF Header                 │  魔数 + 版本号
├──────────────────────────────┤
│  Metadata (key-value pairs)  │  模型信息（层数、头数等）
│  - general.architecture      │
│  - llama.context_length      │
│  - llama.embedding_length    │
│  - llama.block_count         │
│  - ...                       │
├──────────────────────────────┤
│  Tensor Info                 │  每个张量的位置和类型
│  - token_embd: Q4_K_M       │
│  - blk.0.attn_q: Q4_K_M     │
│  - blk.0.ffn_gate: Q4_K_M   │
│  - ...                       │
├──────────────────────────────┤
│  Alignment Padding           │  内存对齐（CPU 加速用）
├──────────────────────────────┤
│  Tensor Data                 │  实际的量化权重数据
│  - token_embd 权重 (Q4_K_M) │
│  - blk.0.attn_q 权重         │
│  - ...                       │
└──────────────────────────────┘

为什么 metadata 用 key-value？
  → 新增字段（如新增一种位置编码）不会破坏旧文件的解析
  → 解析器跳过不认识的 key 就行
  → 比 GGML 的固定偏移量灵活得多
```

### GGUF 的 CPU 优化技巧

```
1. 内存映射（mmap）
  GGUF 文件可以直接 mmap 到内存
  → 不需要把整个文件读入 RAM
  → 按需加载，10GB 的模型只需要 2-3GB 的 RAM 就能跑
  
  类比：
    mmap = 不把整本书读完，而是翻到哪页读哪页
    传统加载 = 先把整本书抄一遍到笔记本上

2. 逐层解量化
  推理时只解量化当前需要的层
  → 不需要一次性把所有权重都反量化
  → CPU 的 L2/L3 缓存友好

3. SIMD 加速
  llama.cpp 大量使用 AVX2/AVX-512/NEON 指令
  → 一条指令同时处理 4-8 个 INT8/INT4 运算
  → 单核性能接近 GPU 的 1/10

4. 线程并行
  多核 CPU 上，矩阵乘法按行分给不同线程
  → 8 核 CPU 大约 3-5 倍加速
```

## 🔧 BitsAndBytes：训练时的量化搭档

> ❓ **问题**：GPTQ、AWQ、GGUF 都是推理时用的量化方案。但如果我不仅要推理，还想在量化后的模型上做微调（比如 QLoRA），需要什么？

**BitsAndBytes**（简称 BnB）就是为此而生的——它是 QLoRA 的底层引擎，提供训练友好的量化。

### BnB 的两种核心格式

```
1. LLM.int8() — 8-bit 推理 + 训练

  核心创新：混合精度分解
  
  观察：Transformer 前向传播时，激活值中大约 0.1% 是"极端值"（>6σ）
  问题：这些极端值让 INT8 量化的 scale 变得很大 → 其他值的精度下降
  
  LLM.int8() 的方案：
    把矩阵乘法拆成两部分：
    
    a) 正常值（99.9%）：用 INT8 矩阵乘法（快，省内存）
    b) 极端值（0.1%）：用 FP16 矩阵乘法（精确，但只处理少量数据）
    
    最后把两部分结果加起来
  
  效果：
    → 几乎零精度损失（比纯 INT8 好 10 倍）
    → 内存节省 50%（FP16 → INT8）
    → 速度只慢 ~5%（混合精度的额外开销）

2. NF4（NormalFloat 4-bit）— 4-bit 量化
  
  我们在 Day 21 QLoRA 里详细介绍过 NF4：
    → 专门为正态分布设计的量化格式
    → 量化级别等间距分布在 [-1, 1] 的正态分位数上
    → 比"均匀间距"的 INT4 更适合神经网络权重
    → 配合双量化（Double Quantization）进一步压缩 scale
```

### BnB vs GPTQ vs AWQ：定位差异

```
┌──────────────────────────────────────────────────────────────┐
│  维度          │  BnB/NF4     │  GPTQ        │  AWQ         │
├──────────────────────────────────────────────────────────────┤
│  主要用途      │  训练时量化   │  纯推理量化   │  纯推理量化   │
│  典型场景      │  QLoRA 微调  │  GPU 部署     │  GPU 部署     │
│  需要校准数据  │  ❌ 不需要    │  ✅ 128 条    │  ✅ 128 条    │
│  量化时间      │  即时（在线） │  几分钟~几小时 │  几分钟       │
│  精度（INT4）  │  好          │  很好         │  最好         │
│  推理速度      │  中等        │  快           │  快           │
│  训练支持      │  ✅ 原生     │  ❌ 不支持    │  ❌ 不支持    │
│  代表项目      │  QLoRA       │  auto-gptq    │  AutoAWQ      │
│  依赖框架      │  PyTorch     │  auto-gptq    │  AutoAWQ      │
└──────────────────────────────────────────────────────────────┘

关键区别：
  BnB = "边用边量化"（runtime quantization）
  GPTQ = "离线量化好，在线直接用"（offline quantization）
  AWQ = "离线量化好，用缩放保护重要权重"（offline + scaling）
```

## 🧩 混合精度量化：不把鸡蛋放在一个篮子里

> ❓ **问题**：上面我们介绍了三种主流方案，它们各有优劣。能不能把它们的优点组合起来？

**混合精度量化（Mixed-Precision Quantization）** 就是这个思路——不同的层用不同的精度。

### 为什么要混合精度？

```
统一 INT4 量化的问题：
  Embedding 层：INT4 损失大 → 模型"认字"能力下降
  Q/K 投影：INT4 损失大 → 注意力分配混乱
  FFN 层：INT4 损失小 → 完全没问题
  输出层：INT4 损失中 → 生成质量略降

如果统一 INT8：
  所有用 INT8 → 精度好，但体积大（7GB for 7B）
  
混合精度方案：
  Embedding + Q/K → INT8（保护精度）
  FFN 中间层 → INT4（压缩体积）
  输出层 → INT6（折中）
  
  结果：平均精度 ≈ 5-bit，体积 ≈ INT4 的 1.1 倍，但精度接近 INT8

这就是 GGUF 的 K-quant（Q4_K_M 等）背后的思想：
  不是所有层都用 4-bit，而是按重要性分配不同精度
```

### 如何决定每层用什么精度？

```
方法 1：基于敏感度分析（AWQ 风格）
  → 跑校准数据，统计每层的量化误差
  → 误差大的层用高精度，误差小的层用低精度

方法 2：基于 Hessian 迹（GPTQ 风格）
  → 计算 Hessian 矩阵的迹（trace）
  → 迹大的层 → 权重更敏感 → 用高精度

方法 3：试错搜索
  → 从全 INT4 开始，逐层提升精度，看哪个组合效果最好
  → 简单粗暴，但计算量大

方法 4：规则启发式
  → Embedding 和首尾层 → INT8
  → Attention 投影 → INT6
  → FFN → INT4
  → 不需要搜索，实践中效果已经很好

实际方案中，GGUF 的 K-quant 用的是方法 4（预设规则）
AWQ 用的是方法 1（基于激活值）
GPTQ 可以结合方法 2
```

## 📊 实战对比：三大方案的量化效果

> ❓ **问题**：说了这么多理论，AWQ、GPTQ、GGUF 在实际模型上到底差多少？

```
以 LLaMA-2-7B 为例（WikiText-2 perplexity，越低越好）：

方法              │  每参数字节  │  模型大小  │  PPL    │  vs FP16
─────────────────────────────────────────────────────────────────
FP16 (基准)       │  2.00       │  13.5 GB  │  5.47   │  —
─────────────────────────────────────────────────────────────────
INT8 (BnB)        │  1.00       │  6.7 GB   │  5.48   │  +0.01
─────────────────────────────────────────────────────────────────
GPTQ (INT4)       │  0.50       │  3.9 GB   │  5.64   │  +0.17
AWQ (INT4)        │  0.50       │  3.9 GB   │  5.60   │  +0.13
GGUF Q4_K_M       │  0.58       │  4.1 GB   │  5.62   │  +0.15
GGUF Q5_K_M       │  0.69       │  4.8 GB   │  5.55   │  +0.08
─────────────────────────────────────────────────────────────────
GGUF Q3_K_M       │  0.43       │  3.1 GB   │  5.85   │  +0.38
GGUF Q2_K         │  0.33       │  2.4 GB   │  6.45   │  +0.98

关键结论：
  1. INT4 量化后 PPL 只增加 0.1-0.2，完全可用
  2. AWQ 整体最优（PPL 最低）
  3. GPTQ 也很强，且生态更成熟
  4. GGUF Q4_K_M 考虑到能在 CPU 跑，性价比极高
  5. Q2_K 虽然体积最小，但 PPL 增加 1.0 → 明显退步
```

### 不同场景的最佳选择

```
场景 1：有 GPU，追求最高精度
  → AWQ INT4
  → 推理速度最快，精度最好

场景 2：有 GPU，快速部署
  → GPTQ INT4
  → 社区预量化模型最多，拿来即用

场景 3：没有 GPU（笔记本/服务器 CPU）
  → GGUF Q4_K_M 或 Q5_K_M
  → CPU 推理唯一选择，效果很好

场景 4：要微调（LoRA/QLoRA）
  → BitsAndBytes NF4 + LoRA
  → 训练时动态量化，内存最低

场景 5：手机/嵌入式
  → GGUF Q3_K_M 或 Q4_0
  → 体积小，llama.cpp 支持移动端

场景 6：多用户并发服务
  → AWQ INT4 + vLLM
  → 批处理效率最高

总结：没有"最好的"量化方案，只有"最适合"的
```

> ❓ **问题**：理论讲了很多，让我们亲手实现 AWQ 的核心思想——找到重要权重并缩放保护，然后对比不同量化方案的效果。

今天的代码实现：

2. **量化效果对比**：线性量化 vs AWQ 风格量化 vs 逐通道量化
3. **模拟混合精度**：不同层用不同精度，观察综合效果
4. **GGUF 模型大小估算**：不同 K-quant 类型的体积计算
5. **BitsAndBytes NF4 模拟**：理解正态分布优化量化

完整代码见 `advanced_quantization.py`。

## 🔑 关键洞察

1. **线性量化的瓶颈是离群值**：少数极端权重决定了 scale，导致大多数权重精度下降
2. **GPTQ 用 Hessian 信息做误差补偿**：量化一个权重后，调整剩余权重来"弥补"——像裁缝改衣服
3. **AWQ 更聪明：直接缩放重要通道**：给重要权重乘以缩放因子，让它们在量化时天然更安全——简单且高效
4. **GGUF 是 CPU 推理之王**：混合精度（K-quant）+ mmap + SIMD，让 7B 模型在笔记本上流畅运行
5. **BitsAndBytes 是训练之友**：LLM.int8() 和 NF4 为 QLoRA 等训练场景提供在线量化
6. **没有万能方案**：AWQ 追求精度、GPTQ 追求生态、GGUF 追求 CPU 兼容、BnB 追求训练支持——按场景选择

---

## 📝 一句话总结

> 线性量化对"所有权重一视同仁"，而进阶量化方案各有各的"聪明劲儿"：GPTQ 像"边裁边补"的裁缝，量化一个权重就调整其余权重来补偿误差；AWQ 像"重点保护"的保镖，找到重要权重（用激活值判断）并给它们穿上缩放的铠甲；GGUF 像"灵活打包"的行李专家，不同层用不同精度来适配 CPU 推理；BitsAndBytes 像"边用边压"的运行时引擎，让 QLoRA 能在 4-bit 模型上直接训练。没有最好的方案，只有最适合你硬件和需求的方案。

## 📖 关键术语速查

| 术语 | 含义 |
|------|------|
| **GPTQ** | 基于 Hessian 的训练后量化，逐层量化并补偿误差 |
| **AWQ** | 基于激活感知的权重量化，缩放重要通道来保护精度 |
| **GGUF** | llama.cpp 的模型格式，支持 20+ 种量化类型，专为 CPU 优化 |
| **K-quant** | GGUF 的混合精度量化，不同层用不同 bit 数（如 Q4_K_M） |
| **BitsAndBytes** | PyTorch 量化库，提供 LLM.int8() 和 NF4 两种格式 |
| **NF4** | 正态分布优化的 4-bit 格式，量化级别按正态分位数分布 |
| **LLM.int8()** | BnB 的 8-bit 方案，混合精度分解（99.9% INT8 + 0.1% FP16） |
| **Salient Weights** | AWQ 中定义的"重要权重"，由权重 × 激活值的乘积大小决定 |
| **Hessian 矩阵** | 损失函数的二阶导数矩阵，衡量每个权重对损失的"敏感度" |
| **混合精度量化** | 不同层或不同权重使用不同精度的量化策略 |
| **mmap** | 内存映射技术，GGUF 用它实现按需加载模型，不需要全部读入 RAM |
| **校准数据** | 量化时用于统计激活值/Hessian 信息的少量样本（通常 128 条） |

> 🤔 **今天留下的悬念**：我们学会了怎么把一个大模型"压"到很小——INT4 让 7B 模型只要 3.5GB。但"压缩"只是手段，不是目的。还有一种完全不同的思路：与其训练一个大模型再压缩，不如直接训练多个小模型来协作——每个小模型只处理一部分输入，既不牺牲总参数量，又不需要每个样本都激活所有参数。这就是 **MoE（Mixture of Experts）** 的思想，混合专家模型——明天我们来拆解这个"模型界的联合办公"架构。
